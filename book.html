System design আসলে কী?

চায়ের দোকান বড় হলে শুধু বড় কেটলি নয়—অর্ডার নেওয়া, টাকা রাখা ও পরিবেশনের ব্যবস্থাও বদলায়। Software-এ সেই ব্যবস্থার নকশাই system design।

ধারণা ও কাজের ধাপ

একটি system-এ client, API, database, file storage ও background worker বিভিন্ন দায়িত্ব নেয়। Design মানে কোন দায়িত্ব কোথায় থাকবে, কীভাবে যোগাযোগ করবে এবং একটি অংশ বন্ধ হলে অন্য অংশ কী করবে তা ঠিক করা।

HLD-তে বড় component ও data flow দেখবেন। LLD-তে একটি component-এর module, interface, state ও validation দেখবেন। প্রথমে সবচেয়ে সহজ design বানান যা requirements মেটায়। Bottleneck-এর প্রমাণ পেলে component যোগ করুন।

ব্যবহারকারী↓API / business rules↓ডেটা↓ফলাফল

উদাহরণ

১০০ user-এর booking app একটি backend ও PostgreSQL দিয়ে শুরু করতে পারে। Confirmation email ধীর হলে পুরো app microservice না করে email-কে worker-এ নেওয়াই যথেষ্ট হতে পারে।

কখন ব্যবহার করবেন

নতুন feature, production সমস্যা, scaling বা migration—সব ক্ষেত্রেই design চিন্তা লাগে। Interview-তেও একই চিন্তা পরিষ্কারভাবে প্রকাশ করবেন।

Trade-off

কম component পরিচালনা সহজ করে। আলাদা component স্বাধীন scaling দেয়, কিন্তু network, deployment ও debugging জটিল করে।

সাধারণ ভুল

সব diagram-এ Kafka, Kubernetes ও microservices বসিয়ে দেওয়া; অথচ workload বা সমস্যাটি জানা নেই।

নিজে করুন

আপনার পরিচিত একটি app নিন। Client, API, database ও external service আঁকুন। প্রতিটি arrow-এ কী data যায় এবং কোন failure সম্ভব লিখুন।

মনে রাখুন

প্রথমে সমস্যা → তারপর সিদ্ধান্ত → শেষে প্রযুক্তি।

Requirements ও scope

“একটা booking app বানাব”—এটি feature-এর নাম; design শুরু করার মতো specification নয়।

ধারণা ও কাজের ধাপ

Functional requirement বলে কী কাজ হবে: slot দেখা, booking, cancellation। Non-functional requirement বলে কাজ কত দ্রুত, নিরাপদ ও নির্ভরযোগ্য হতে হবে। Business invariant হলো যেটি কখনো ভাঙতে দেবেন না—একটি slot দুজনের কাছে confirm হবে না।

Must-have, later এবং out-of-scope লিখুন। User journey ধরে success criteria ঠিক করুন। “দ্রুত” না বলে নির্দিষ্ট workload-এ p95 response time-এর target লিখুন। এগুলো প্রাথমিক assumption; বাস্তব measurement ও stakeholder-এর প্রয়োজন অনুযায়ী বদলাবে।

User journey↓Functional scope↓Quality target↓Invariant

উদাহরণ

একটি clinic app-এ receptionist patient-এর booking বদলাতে পারবেন, patient অন্যের medical note দেখতে পারবেন না। “Booking দ্রুত” এবং “double booking হবে না”—দুটি আলাদা requirement।

কখন ব্যবহার করবেন

Coding-এর আগে, interview-এর শুরুতে এবং scope বদলালে এই তালিকা পুনরায় দেখুন।

Trade-off

খুব বেশি scope delivery ধীর করে। কম scope দ্রুত value দেয়, কিন্তু বাদ দেওয়া capability পরিষ্কার জানাতে হবে।

সাধারণ ভুল

Availability-এর target সব operation-এ একই ধরে নেওয়া; report download ও emergency booking-এর গুরুত্ব এক নয়।

নিজে করুন

একটি clinic-এর জন্য ৫টি functional, ৪টি non-functional requirement এবং ৩টি invariant লিখুন। Payment আপাতত scope-এর বাইরে রাখুন।

কী করবে + কত ভালো করবে + কী কখনো ভুল হবে না।

Capacity estimation: সংখ্যা দিয়ে ভাবুন

দোকানে দৈনিক কত customer আসে জানলেই দুপুরের ভিড় বোঝা যায় না। Average traffic আর peak traffic আলাদা।

ধারণা ও কাজের ধাপ

Average RPS = daily requests / 86,400। DAU-কে প্রতি user-এর দৈনিক request দিয়ে গুণ করে daily requests ধরতে পারেন। Peak factor একটি assumption; বাস্তব traffic না থাকলে তা স্পষ্ট লিখুন।

Storage হিসাব করুন record count × average record size। এরপর indexes, replication, logs, backups ও retention আলাদা যোগ করুন। Bandwidth-এর জন্য responses per second × average payload size ধরুন। Estimates capacity planning-এর শুরু, benchmark-এর বিকল্প নয়।

DAU × request↓Daily workload↓÷ 86,400↓Average / peak

উদাহরণ

১ লাখ DAU × ২০ request = ২০ লাখ request/day ≈ ২৩.১ average RPS। Peak ৫ গুণ ধরলে প্রায় ১১৬ RPS। প্রতিটি request একই খরচের নয়; search ও cached read আলাদা।

কখন ব্যবহার করবেন

কোন component আগে পরীক্ষা করবেন, কত storage বাড়বে বা image delivery-তে CDN দরকার কি না—এমন সিদ্ধান্তে।

Trade-off

বেশি headroom খরচ বাড়ায়, কম headroom sudden spike-এ overload তৈরি করতে পারে।

সাধারণ ভুল

Registered user-কে concurrent user ধরে নেওয়া; KB ও KiB অথবা bits ও bytes এক করে ফেলা।

নিজে করুন

ল্যাবে DAU, request ও payload বদলান। তারপর নিজের project-এর average এবং peak estimates লিখে assumptions যোগ করুন।

Latency, throughput ও tail latency

একজন customer-এর অপেক্ষার সময় latency; প্রতি মিনিটে কত customer সেবা পেলেন তা throughput।

ধারণা ও কাজের ধাপ

Average একা slow user-এর অভিজ্ঞতা ঢেকে দেয়। p95 = যে সময়ের মধ্যে ৯৫% request শেষ হয়েছে; বাকি ৫% আরও ধীর হতে পারে। p99-এর মান p95-এর নিচে হওয়া উচিত নয়।

Sequential call-এর latency যোগ হয়; independent parallel call-এ মোট সময় প্রায় সবচেয়ে ধীর call-এর সময়, সঙ্গে overhead। Steady-state-এ Little’s Law: average in-flight ≈ throughput × average response time। এটি average-এর সম্পর্ক; p95 বসিয়ে সরাসরি একই ফল দাবি করবেন না।

Load generation-এ closed-loop concurrency আর open-loop arrival rate এক নয়। Slow response হলে closed-loop client নিজে request কম পাঠাতে পারে, overload আড়াল হয়। Benchmark-এ arrival model, warmup, achieved throughput, timeout/error ও percentile distribution লিখুন। Coordinated omission-এর মতো measurement bias সম্পর্কে পরিচিত হন।

Request↓Network↓API ও dependency↓Response

উদাহরণ

API প্রথমে DB-তে ৮০ ms, তারপর payment-এ ২০০ ms অপেক্ষা করলে শুধু ওই dependency-তেই ২৮০ ms যায়। Independent profile ও preferences parallel আনা যায়; dependent payment confirmation আগে আনা যায় না।

কখন ব্যবহার করবেন

Performance target, timeout এবং slow request debug করার সময়।

Trade-off

বড় batch throughput বাড়াতে পারে কিন্তু প্রথম user-এর অপেক্ষা বাড়ায়। বেশি concurrency resource saturation-ও তৈরি করতে পারে।

সাধারণ ভুল

Average ভালো মানেই সবাই ভালো experience পাচ্ছে বলা; p95 কমাতে না মেপে server বাড়ানো।

নিজে করুন

১০০টি response time সংগ্রহ করে p50/p95/p99 বের করুন। Load দ্বিগুণ করে error ও tail latency কীভাবে বদলায় লিখুন।

PACELC: partition ছাড়াও trade-off

শুধু network ভাঙলে নয়, সব ঠিক থাকলেও দূরের copy-এর confirmation-এর অপেক্ষা response ধীর করতে পারে।

ধারণা ও কাজের ধাপ

CAP partition-এর সময় availability বনাম consistency-এর সীমা বোঝায়। PACELC-এর সহজ পাঠ: Partition হলে A/C trade-off; Else normal operation-এ Latency/Consistency trade-off। এটি product বেছে নেওয়ার slogan নয়, নির্দিষ্ট operation-এর coordination cost ব্যাখ্যার lens।

এক region-এর local write দ্রুত হতে পারে। অন্য region-এ synchronous confirmation চাইলে round-trip time ও দূরের region-এর health নির্ভরতা যোগ হয়। একই product বিভিন্ন configuration/operation-এ ভিন্ন guarantee দিতে পারে। Read/write policy, replication mode ও conflict handling আলাদাভাবে লিখুন।

Client connection↓Gateway↓Message store↓Reconnect ও sync

ফোনবুকে নাম থেকে number পাওয়া যায়; DNS নাম থেকে network address খুঁজে পেতে সাহায্য করে।

ধারণা ও কাজের ধাপ

Browser/OS cache, recursive resolver, root/TLD delegation ও authoritative nameserver—cache miss হলে এই chain-এর প্রয়োজনীয় অংশ resolve হয়। A/AAAA address, CNAME alias, MX mail routing, TXT verification-এর মতো আলাদা record type আছে। CNAME-কে IP record ভেবে বসবেন না।

TTL cached answer কতক্ষণ ব্যবহারযোগ্য তার নির্দেশ দেয়। DNS change সব client-এ এক মুহূর্তে পৌঁছায় না। Negative caching-এ missing name-ও কিছু সময় মনে থাকতে পারে। DNS failover existing TCP/WebSocket connection সরায় না; client reconnect ও resolver cache বিবেচনা করতে হয়।

Local cache↓Recursive resolver↓Authoritative answer↓TTL-cached address

ধারণা ও কাজের ধাপ

TCP ordered reliable byte stream, congestion control ও retransmission দেয়; application message boundary নিজে দেয় না। UDP datagram-এ সেই guarantee নিজে নেই। UDP ব্যবহারকারী application protocol প্রয়োজনমতো reliability implement করতে পারে। “UDP মানে সবসময় unreliable app” বলা ভুল।

HTTP/1.1-এ connection reuse থাকলেও parallelism-এর limits আছে। HTTP/2 একই TCP connection-এ multiplexed streams দেয়, তবে TCP packet loss সব stream-এ delay ফেলতে পারে। HTTP/3 QUIC over UDP ব্যবহার করে independent stream delivery উন্নত করে; encryption, network ও implementation constraints এখনও থাকে।

Application message↓HTTP / other protocol↓TCP বা QUIC/UDP↓Application acknowledgement

সাধারণ ভুল

নিজে করুন

ধারণা ও কাজের ধাপ

REST resource-oriented interface ও HTTP semantics ব্যবহার করতে পারে। GraphQL client-কে schema থেকে selected fields চাওয়ার সুযোগ দেয়; resolvers-এ N+1, query depth, authorization ও cost limit দরকার। gRPC protobuf contract ও streaming support দিয়ে internal typed communication-এ কার্যকর হতে পারে।

Versioning, backward-compatible schema evolution, deadlines, cancellation ও error mapping communication contract-এর অংশ। GraphQL-এর একটি endpoint থাকলেই monitoring সহজ নয়; operation-level metrics লাগবে। gRPC ব্যবহার করলেই network failure বা duplicate request দূর হয় না।

Serialization-এ JSON human-readable ও broad tooling দেয়; protobuf typed schema ও compact encoding দিতে পারে, কিন্তু field-number/schema compatibility রক্ষা করতে হয়। Compression যেমন gzip/Brotli bytes কমায় কিন্তু CPU ও latency খরচ যোগ করে; already-compressed media-তে লাভ কম হতে পারে। Payload size, parse time ও compress cost মেপে সিদ্ধান্ত নিন।

Consumer requirement↓Contract / schema↓Authorization + limits↓Observed API behaviour

উদাহরণ

Public booking CRUD REST-এ সহজ। Dashboard-এর বহু entity aggregation GraphQL দিয়ে করা যায়; read amplification পরীক্ষা করুন। Internal low-latency typed calls-এ gRPC বিবেচ্য, browser/client support পরিকল্পনাসহ।

কখন ব্যবহার করবেন

Client needs, team boundaries, tooling ও operational capacity ভিন্ন হলে।

Trade-off

Flexibility বনাম predictable cost; compact typed protocol বনাম integration simplicity।

একটিকে সব system-এর universal replacement বলা।

নিজে করুন

তিন API style-এ list booking, errors ও pagination-এর contract sketch করুন। কোনটি কেন নেবেন লিখুন।

Rate limiting: window, token ও leaky bucket

দরজায় কতজন ঢুকতে পারবেন, কত দ্রুত পারবেন, আর হঠাৎ ভিড় কতটা মেনে নেবেন—এই তিন প্রশ্ন আলাদা।

ধারণা ও কাজের ধাপ

Fixed window সহজ counter, কিন্তু boundary-তে দুই window-এর burst হতে পারে। Sliding log timestamps ধরে precise window দেয়, memory বেশি। Sliding counter দুই window-এর weighted estimate দেয়। Token bucket সময়ের সঙ্গে refill হয়, capacity পর্যন্ত burst allowance ধরে। Leaky bucket নির্দিষ্ট drain দিয়ে smoothing বোঝায়।

Key হতে পারে tenant/user/API key/IP। Shared NAT-এ IP-only policy নির্দোষ user block করতে পারে। Distributed limiter-এ refill+check+decrement atomic হতে হবে। Failure-এ fail-open বা fail-closed operation risk অনুযায়ী লিখুন। HTTP 429 ও retry guidance client-কে দিন।

Client identity↓Atomic refill + check↓Allow / 429↓Metrics + policy

Capacity 5, refill 1 token/s। প্রথমে ৫টি immediate request নেয়, ষষ্ঠটি reject। ২ সেকেন্ড পরে ২টি token ফেরে; কিন্তু maximum ৫-এর বেশি জমে না।

Trade-off

Precision, state size, burst tolerance ও coordination cost-এর মধ্যে নির্বাচন।

Scaling ও traffic management · নতুন পাঠ

Vertical, horizontal scaling ও Amdahl’s Law

একজন দ্রুত কর্মী নেবেন, নাকি আরও কর্মী? কাজ ভাগ করা না গেলে শুধু কর্মী বাড়িয়ে লাভ সীমিত।

ধারণা ও কাজের ধাপ

Vertical scaling একটি machine-এর CPU/RAM/IO capacity বাড়ায়। Horizontal scaling instance বাড়ায়। Stateless work তুলনামূলক সহজে ভাগ হয়; shared state, serialization ও coordination limits থেকে যায়। Throughput scaling ও availability improvement একই guarantee নয়।

Amdahl’s Law-এর simplified bound: speedup = 1 / ((1−p)+p/n), p parallelizable fraction, n workers। এটি workload assumption, real benchmark নয়। Database locks, global mutex বা shared provider quota serial bottleneck তৈরি করতে পারে। Capacity পরিবর্তনের আগে saturation evidence দেখুন।

Measure bottleneck↓Scale up / out↓Shared dependency limits↓Load-test again

উদাহরণ

কাজের ৮০% parallel হলে অসীম worker দিয়েও theoretical speedup সর্বোচ্চ ৫×। ১০টি web instance একই saturated DB-তে call করলে সেই bottleneck বাড়তে পারে।

Capacity planning ও “আরও server” প্রস্তাব যাচাইয়ে।

Trade-off

Vertical সহজ কিন্তু machine ceiling ও failure concentration; horizontal flexible কিন্তু data coordination খরচ।

সাধারণ ভুল

দ্বিগুণ instance মানেই দ্বিগুণ throughput বলা।

নিজে করুন

CPU-heavy worker ও transaction-heavy API-এর scaling constraints আলাদা লিখুন।

মনে রাখুন

আরও server-এর আগে serial bottleneck খুঁজুন।

ধারণা ও কাজের ধাপ

L4 load balancer transport-level information যেমন IP/port/connection দেখে routing করে। L7 application-aware হয়ে HTTP path, host, headers বা cookies অনুযায়ী route করতে পারে। TLS কোথায় terminate হচ্ছে তার ওপর request inspect করার সুযোগ নির্ভর করে। TLS passthrough ও terminate/re-encrypt আলাদা topology।

Client identity propagate করতে trusted proxy chain ও forwarding-header policy দরকার। Untrusted X-Forwarded-For বিশ্বাস করলে rate limit/audit spoof হতে পারে। Connection-level balancing-এ দীর্ঘ HTTP/2 বা WebSocket connection workload অসমান রাখতে পারে।

Client TLS↓L4 passthrough / L7 terminate↓Backend routing↓Trusted identity headers

Trade-off

Round robin, weighted, least connections ও IP hash

সমান request count সবসময় সমান কাজ নয়। ছোট query আর মিনিটব্যাপী stream-এর খরচ ভিন্ন।

ধারণা ও কাজের ধাপ

Round robin পালাক্রমে instance বেছে নেয়। Weighted routing capacity অনুযায়ী share দেয়। Least connections সক্রিয় connection কম আছে এমন node নেয়, তবে connection count CPU work-এর নিখুঁত proxy নয়। IP hash affinity দেয়, কিন্তু NAT ও client concentration imbalance করতে পারে।

Request duration, instance heterogeneity ও session locality দেখে algorithm বেছে নিন। Consistent routing চাইলে node membership change-এর remapping ভাবুন। Sticky session failover-এ state হারানো বা hotspot-এর risk রাখে। Measured queue length বা response latency-based policy-তেও noisy metrics-এর feedback loop সামলাতে হয়।

Traffic characteristics↓Choose routing policy↓Observe utilization↓Rebalance / isolate pools

Trade-off

কর্মী উপস্থিত আছেন মানেই নতুন customer সামলানোর মতো প্রস্তুত নন।

ধারণা ও কাজের ধাপ

Liveness বলে process stuck কি না; readiness বলে traffic নিতে প্রস্তুত কি না। Startup probe slow initialization চলাকালে premature restart আটকাতে পারে। Shallow endpoint process দেখলেও business dependency-এর প্রয়োজনীয় readiness পরীক্ষা বাদ পড়তে পারে। আবার সব dependency liveness-এ দিলে অন্য service-এর outage-এ restart storm হতে পারে।

Health detection interval, timeout, threshold ও recovery hysteresis লিখুন। Deployment-এ readiness off → routing remove → in-flight drain → terminate। Endpoint removal ও active connection-এর behaviour proxy/client অনুযায়ী ভিন্ন। Failover-এ stale state/duplicates possible, তাই retry safety জরুরি।

Startup↓Readiness on↓Drain new traffic↓Finish / terminate

Stateless service ও shared state

যেকোনো counter একই order handle করতে পারলে counter বাড়ানো সহজ হয়।

ধারণা ও কাজের ধাপ

Stateless instance request-এর মধ্যে authoritative user/session/business state নিজ memory-তে নির্ভরযোগ্যভাবে ধরে না। State নেই এমন নয়—database, object storage বা shared session store-এ থাকে। Local cache পুনর্গঠনযোগ্য হতে পারে।

Request-এ প্রয়োজনীয় identity/context আসে, backend authoritative state পড়ে। File upload local disk-এ রেখে পরের request অন্য instance-এ গেলে missing file হতে পারে। Background job scheduling প্রতিটি API instance-এ চালালে duplicate run হতে পারে। External state store নিজেই capacity ও availability dependency।

Any instance↓Request identity↓Shared authoritative state↓Disposable local cache

উদাহরণ

নিজে করুন

Modular monolith: শুরুটা গুছিয়ে করুন

একটি বাড়ি মানেই সব ঘর একসঙ্গে মিশে থাকা নয়। একই application-এর মধ্যেও booking, billing ও identity পরিষ্কার module হতে পারে।

ধারণা ও কাজের ধাপ

Monolith একটি deployment unit। Modular monolith-এ business capability অনুযায়ী boundary থাকে; module অন্য module-এর internals না ধরে public interface ব্যবহার করে। Database একই হলেও table ownership ও dependencies পরিষ্কার রাখা যায়।

Request/controller, business rules এবং data access আলাদা দায়িত্ব নেবে। Module boundary শুধু folder নয়—অনুমোদিত dependency ও test-এ তা ধরে রাখতে হয়। বাস্তব constraint ছাড়া generic abstraction বানাবেন না।

Maintainability-তে module ownership, small explicit interfaces, dependency review, readable code ও automated checks গুরুত্বপূর্ণ। Performance-critical path-এ suitable data structures যেমন hash-map lookup, heap priority queue ও trie prefix lookup cost আলাদা। Big-O input growth বোঝায়, constant factors/cache/IO বাস্তব measurement-এ আসে।

HTTP layer↓Booking module↓Billing interface↓Database ownership

উদাহরণ

Booking module availability ও reservation সামলায়। Billing module invoice তৈরি করে। Booking সরাসরি billing-এর private table বদলালে boundary ভাঙে; interface বা event ব্যবহার করা যায়।

ছোট/মাঝারি team, দ্রুত পরিবর্তনশীল product, সীমিত operational capacity।

Trade-off

Single deploy সহজ ও local transaction সুবিধাজনক। তবে uncontrolled coupling হলে এক feature-এর পরিবর্তন অন্যটিকে ভাঙতে পারে।

সাধারণ ভুল

নিজে করুন

Index ও query plan

বইয়ের সূচি দিয়ে পৃষ্ঠা খোঁজা সহজ; কিন্তু প্রতিটি শব্দের জন্য আলাদা সূচি রাখলে বই রক্ষণাবেক্ষণ কঠিন হয়।

ধারণা ও কাজের ধাপ

Index database-কে কিছু query-তে কম row/page পরীক্ষা করতে সাহায্য করে। Composite B-tree index-এর column order query predicate ও ordering-এর সঙ্গে মিলিয়ে ঠিক করুন। Planner ছোট table বা অনেক row ফেরত আসা query-তে sequential scan বেছে নিতে পারে—এটি সবসময় ভুল নয়।

EXPLAIN plan-এর estimates দেখায়; EXPLAIN ANALYZE query চালিয়ে actual rows/timing দেখায়। Actual ও estimated row, scans, sorts, loops ও buffer usage দেখুন। ORM-এর N+1 query আলাদা সমস্যা; index দিয়ে শতবার round trip দূর হয় না।

Composite index order-এর সঙ্গে selectivity ও sort direction বিবেচনা করুন। Covering/index-only scan-এর সুযোগ engine/visibility অনুযায়ী বদলায়। Unbounded offset scan, non-sargable function predicate ও N+1 round trip আলাদা performance problem। Data encoding, wide rows ও unnecessary selected columns memory/network cost বাড়ায়।

SQL query↓Planner↓Index / table scan↓Rows + measured plan

উদাহরণ

WHERE tenant_id=? ORDER BY created_at,id LIMIT 20 query-এর জন্য access pattern অনুযায়ী (tenant_id, created_at, id) index বিবেচনা করুন। Actual plan ও representative data দিয়ে যাচাই করুন।

Trade-off

Transactions, isolation ও double booking

দুই customer শেষ seat দেখলেন। দুজনই আলাদা করে “available” পড়ে booking করলে race condition হয়।

ধারণা ও কাজের ধাপ

Transaction সম্পর্কিত changes একসঙ্গে commit/rollback করে। Atomicity, consistency, isolation, durability-এর অর্থ আলাদা। Isolation level নির্ধারণ করে concurrent transaction কোন পরিবর্তন দেখতে পারে; শুধু BEGIN করলেই সব race বন্ধ হয় না।

একটি atomic conditional update, unique constraint, row lock বা serializable transaction—business rule অনুযায়ী strategy নিন। Optimistic locking version মেলায়; conflict হলে retry বা user-কে জানায়। Lock ordering ও ছোট transaction deadlock risk কমায়। Serializable failure হলে পুরো transaction retry প্রয়োজন হতে পারে।

Isolation levels গভীরে: Read Committed-এ statement ভেদে committed snapshot বদলাতে পারে; Repeatable Read stable snapshot দেয় কিন্তু সব write-skew anomaly প্রতিরোধের guarantee product-independent নয়। Serializable সমতুল্য serial outcome-এর লক্ষ্য নেয়, conflict-এ transaction abort/retry করতে পারে। Read Uncommitted-এর exact implementation product-specific। Deadlock হলে consistent lock order, short transaction এবং whole-transaction retry policy দেখুন।

Read / guard↓Atomic update বা lock↓Booking insert↓Commit / retry

উদাহরণ

এক seat-এর remaining=1। UPDATE ... SET remaining=remaining-1 WHERE remaining>0; affected row এক হলে success। Booking insert একই transaction-এ করুন। Multi-seat বা overlapping interval-এর rule আলাদাভাবে design করতে হবে।

কখন ব্যবহার করবেন

Trade-off

Locks contention বাড়াতে পারে। Optimistic concurrency কম conflict-এ কার্যকর কিন্তু conflict handling লাগে।

সাধারণ ভুল

Read → application check → unconditional write-কে atomic মনে করা।

নিজে করুন

এক seat-এ concurrent request চালান। Unsafe read/write ও atomic update-এর success count তুলনা করুন।

Replication, lag ও read-after-write

মূল খাতার কপি অন্য counter-এ রাখা read ও recovery-তে সাহায্য করে। কিন্তু কপি update হতে সময় লাগলে পুরোনো তথ্য দেখা যায়।

ধারণা ও কাজের ধাপ

Primary-replica setup-এ write primary-তে, eligible read replica-তে যেতে পারে। Asynchronous replication-এ lag থাকে; primary commit-এর পর replica সঙ্গে সঙ্গে data দেখাবে না। Synchronous configuration durability বাড়াতে পারে, তবে latency/availability trade-off থাকে।

Failover-এ নতুন primary নির্বাচন, client reconnect এবং old primary-এর fencing গুরুত্বপূর্ণ। Replica backup-এর বিকল্প নয়: accidental deletion replicate-ও হতে পারে। Read-your-writes প্রয়োজন হলে session-এর critical read primary-তে পাঠানো একটি option।

Replication topology আরও আছে: multi-leader-এ একাধিক leader writes নেয়, concurrent conflicts ও conflict resolution দরকার। Leaderless-style store একাধিক replica-তে read/write policy চালাতে পারে; quorum/repair rules গুরুত্বপূর্ণ। Single-leader-এ write ordering সহজ হতে পারে, কিন্তু leader failover/throughput bottleneck আসে। Topology নাম alone durability guarantee নয়।

Write → primary↓Replication stream↓Replica read↓Lag ও failover

উদাহরণ

User profile edit করলেন, তারপর refresh-এ পুরোনো নাম দেখলেন। Replica lag হতে পারে। Payment confirmation বা booking success-এর immediate read primary-তে রাখা যুক্তিযুক্ত হতে পারে।

কখন ব্যবহার করবেন

Trade-off

বেশি replica read capacity দেয় কিন্তু lag, infrastructure cost ও operational complexity বাড়ায়।

সাধারণ ভুল

Replication আছে মানেই zero data loss বা backup দরকার নেই বলা।

নিজে করুন

খাতা বড় হলে পাতা ভাগ করা আর বিভিন্ন শাখায় খাতা ভাগ করা এক নয়। Data ভাগ করার সঙ্গে routing ও rebalancing আসে।

ধারণা ও কাজের ধাপ

Partitioning logical dataset ভাগ করে, একই database-এও হতে পারে। Sharding সাধারণত data একাধিক database/server-এ ভাগ করে। Tenant ID, user ID বা hash key অনুযায়ী routing করা যায়। Shard key access pattern ও distribution-এর সঙ্গে মিলতে হবে।

Hash distribution সমান করতে সাহায্য করে, কিন্তু বড় tenant বা জনপ্রিয় item hot হতে পারে। Cross-shard joins/transactions কঠিন। Consistent hashing node change-এ remapping সীমিত করতে পারে; hot key-এর সম্পূর্ণ সমাধান নয়। Resharding-এ copy, catch-up, route switch ও rollback plan লাগে।

Routing key↓Shard router↓Shard A / B / C↓Rebalance ও hot key

উদাহরণ

Tenant অনুযায়ী shard করলে tenant-এর query local হতে পারে। একটি tenant সব traffic-এর ৭০% দিলে সেই shard hot হবে; isolated placement বা অন্য split strategy লাগতে পারে।

কখন ব্যবহার করবেন

Trade-off

সাধারণ ভুল

Query optimize ও vertical scaling পরীক্ষা না করেই sharding; shard key পরে সহজে বদলানো যাবে ভাবা।

নিজে করুন

User ID বনাম tenant ID shard key-এর জন্য ৩টি query-এর routing ও একটি hot-tenant scenario তুলনা করুন।

ধারণা ও কাজের ধাপ

Cache-aside-এ প্রথমে cache পড়বেন। Hit হলে ফিরিয়ে দেবেন; miss হলে DB পড়বেন এবং TTL দিয়ে cache ভরবেন। Write path সাধারণত DB update করে cache invalidate করে। Cache key-তে tenant, resource ID ও relevant query parameters রাখুন।

Hit ratio = hits / total lookups। যদি hit path ৫ ms, miss path ১০৫ ms হয়, expected mean ≈ h×5+(1−h)×105। এটি সরল model; contention, payload ও network বদলালে বাস্তব latency আলাদা হবে।

Read cache↓Hit → return↓Miss → DB↓Fill with TTL

উদাহরণ

Caching ও performance · মূল পাঠ

Cache invalidation ও stale data

Database-এ price ১২০, cache-এ ১০০—এই দুই value-এর জীবনচক্র বোঝাই invalidation design-এর মূল।

ধারণা ও কাজের ধাপ

DB commit-এর পরে cache delete একটি common approach। কিন্তু read/write race এখনও হতে পারে: পুরোনো DB value পড়া reader পরে cache refill করলে stale value ফিরে আসতে পারে। TTL, versioned value, event-based invalidation বা stronger coordination প্রয়োজনমতো ব্যবহার করুন।

Write-through cache update synchronously করে; write-behind পরে persist করে, তাই durability ও failure semantics গুরুত্বপূর্ণ। Cache entry, local cache, CDN এবং browser cache আলাদা layer—একটি delete মানেই সব layer clear নয়।

DB commit↓Invalidate key↓Next read miss↓Fresh refill

উদাহরণ

Profile edit-এর response-এ authoritative updated value দিন। UI state update করুন; backend cache invalidation এবং অন্য session-এ freshness policy আলাদা করে ঠিক করুন।

কখন ব্যবহার করবেন

Price, profile, permissions বা frequently changed data cache করলে।

Trade-off

Caching ও performance · নতুন পাঠ

Cache-aside, read-through, write-through ও write-back

কপি পড়া/লেখার দায়িত্ব application নেবে, নাকি cache abstraction? এই ownership-ই pattern বদলায়।

ধারণা ও কাজের ধাপ

Cache-aside application miss পেলে DB পড়ে fill করে। Read-through-এ cache-facing abstraction নিজে data fetch manage করে। Write-through-এ write synchronousভাবে cache/data-store path দিয়ে persist হয়; exact failure semantics implementation অনুযায়ী। Write-back/behind আগে cache-এ accept করে পরে backing store-এ flush করে।

Write-back acknowledge করার আগে durable log না থাকলে process loss-এ acknowledged write হারাতে পারে। শুধু pattern নাম দিয়ে guarantee দাবি করবেন না। Flush ordering, retry, crash recovery ও read consistency contract প্রয়োজন। Write-around DB-তে লেখে, cache next read-এ fill হতে পারে।

Write request↓Synchronous / deferred path↓Cache + backing store↓Ack ও crash recovery

উদাহরণ

Frequently read catalog cache-aside-এ সহজ। Durable financial record-এর একমাত্র copy volatile write-back cache-এ রাখা গ্রহণযোগ্য নাও হতে পারে; durable source of truth আগে ঠিক করুন।

কখন ব্যবহার করবেন

Read/write ratio এবং staleness/durability requirements অনুযায়ী cache integration।

Trade-off

Synchronous persistence write latency বাড়ায়। Deferred persistence throughput বাড়াতে পারে কিন্তু recovery complexity আনে।

সাধারণ ভুল

Write-through মানেই cache/DB একসঙ্গে distributed transaction ছাড়া সবসময় atomic বলা।

নিজে করুন

Write-এর আগে/মাঝে/পরে crash হলে প্রতিটি pattern-এ data কোথায় থাকে table করুন।

মনে রাখুন

Consistency models: কার চোখে কোন data?

একজন নাম বদলে সঙ্গে সঙ্গে পুরোনো নাম দেখলেন। “Data হারিয়েছে” বলার আগে read কোন কপি থেকে এসেছে দেখুন।

ধারণা ও কাজের ধাপ

Strong consistency শব্দের ব্যবহার context অনুযায়ী বদলায়; linearizability-তে operation real-time order-এর সঙ্গে সামঞ্জস্যপূর্ণ একক copy-এর মতো আচরণ করে। Eventual consistency-তে নতুন update থামলে replicas শেষ পর্যন্ত converge করতে পারে, নির্দিষ্ট conflict-resolution assumptions-এর অধীনে।

Read-your-writes user নিজের write দেখতে পাবেন বলে। Monotonic reads-এ নতুন version দেখার পর পুরোনো version দেখবেন না। প্রতিটি workflow-তে guarantee আলাদা হতে পারে; সব data-র একই প্রয়োজন নেই।

Write↓Primary version↓Replica delay↓User-visible guarantee

উদাহরণ

Like count কয়েক সেকেন্ড পুরোনো হওয়া চলতে পারে। Wallet balance spend করার সময় stale replica দেখে সিদ্ধান্ত নিলে double spend risk তৈরি হয়।

কখন ব্যবহার করবেন

Read replica, cache, multi-device sync ও distributed data store design-এ।

Trade-off

Stronger coordination latency বা availability কমাতে পারে; weaker guarantee-তে application complexity ও user confusion বাড়ে।

সাধারণ ভুল

Eventual মানে যেকোনো ভুল data acceptable বলা; convergence ও conflict handling বাদ দেওয়া।

নিজে করুন

Profile, wallet, search index, feed—প্রতিটির consistency requirement লিখে কারণ দিন।

CAP ও network partition

দুই শাখার যোগাযোগ কেটে গেছে। দুজনকে নতুন booking নিতে দিলে conflicting booking হতে পারে; অপেক্ষা করালে কিছু customer সেবা পাবেন না।

ধারণা ও কাজের ধাপ

CAP-এর consistency এখানে linearizability-ধর্মী; availability অর্থ non-failing node-এ প্রতিটি request-এর response পাওয়ার formal property। Network partition-এর সময় উভয় guarantee একসঙ্গে পূরণ করা যায় না। এটি সাধারণ “তিনটির যেকোনো দুইটি” shopping list নয়।

Partition ছাড়া latency ও consistency-এরও trade-off আছে। Design-এ নির্দিষ্ট operation বলুন: কোন write reject/delay করবেন, কোন read stale হলেও চলবে, partition সেরে উঠলে conflicts কীভাবে মেটাবেন।

Region A↓যোগাযোগ বিচ্ছিন্ন↓Region B↓Reject / reconcile policy

উদাহরণ

Inventory reservation-এর disconnected replica দুটোই শেষ item বিক্রি করলে invariant ভাঙতে পারে। Likes গ্রহণ করে পরে merge করা তুলনামূলক গ্রহণযোগ্য হতে পারে।

কখন ব্যবহার করবেন

Multi-node/multi-region system-এর failure behaviour ব্যাখ্যায়।

Trade-off

Write সাময়িক বন্ধ রাখলে correctness রক্ষা হতে পারে, কিন্তু availability ক্ষতিগ্রস্ত। Accept করলে reconciliation দরকার হতে পারে।

সাধারণ ভুল

CAP availability-কে uptime percentage-এর সঙ্গে পুরোপুরি এক মনে করা।

নিজে করুন

একটি payment ও একটি likes feature-এর partition behaviour আলাদাভাবে design করুন। কোন user message দেখাবেন লিখুন।

Distributed IDs, clocks ও ordering

দুই server একই মুহূর্তে নতুন record বানালে ID আলাদা হতে হবে। কিন্তু timestamp সমান বা clock পিছিয়েও যেতে পারে।

ধারণা ও কাজের ধাপ

UUID coordination ছাড়াই identity তৈরির একটি প্রচলিত উপায়; version ও implementation অনুযায়ী ordering/storage behaviour বদলায়। Sequence সহজ কিন্তু central coordination লাগতে পারে। Snowflake-style ID-তে timestamp, worker identity ও counter মিলতে পারে; clock rollback ও worker ID collision handle করতে হয়।

Wall clock দিয়ে distributed event-এর সম্পূর্ণ causal order নিশ্চিত হয় না। Logical clock বা per-entity sequence প্রয়োজনমতো ব্যবহার করুন। Chat-এর conversation sequence আর পুরো বিশ্বের global order এক সমস্যা নয়।

Encoding identity-কে ছোট representation করতে পারে: Base62 সংখ্যা encode করে, encryption নয়। Short code guess করা সম্ভব; authorization-এর বিকল্প নয়। Unique random ID collision probability কমায়, কিন্তু correctness-critical storage-এ unique constraint ও bounded collision retry থাকলে defence বাড়ে।

Event identity↓Node / counter↓Per-entity order↓Deduplicate / sync

উদাহরণ

প্রতিটি chat conversation-এর message sequence রাখা হলে client missing message শনাক্ত করতে পারে। দুটি আলাদা conversation-এর absolute ordering সাধারণত প্রয়োজন হয় না।

কখন ব্যবহার করবেন

Record identity, event deduplication, message ordering ও sync।

Trade-off

Central sequence simple order দেয় কিন্তু coordination cost আছে। Decentralized ID availability ভালো করতে পারে, তবে index locality বা clock assumptions বিবেচনা দরকার।

সাধারণ ভুল

একই millisecond কখনো দুবার আসবে না বা সব server clock একই ধরে নেওয়া।

নিজে করুন

Booking ID ও chat ordering-এর জন্য আলাদা strategy বেছে নিন। Clock পিছালে কী হতে পারে লিখুন।

মনে রাখুন

Unique হওয়া আর ordered হওয়া আলাদা।

Saga, compensation ও reconciliation

Payment হয়েছে, shipment হয়নি। সব service-এর database এক transaction-এ rollback করা সাধারণত সম্ভব নয়।

ধারণা ও কাজের ধাপ

Saga local transaction-এর sequence। প্রতিটি ধাপ সফল হলে পরের ধাপ চলে; ব্যর্থ হলে business compensation হতে পারে। Compensation database rollback-এর মতো নিখুঁত reverse নয়—refund সময় নিতে পারে বা manual review লাগতে পারে।

Orchestration-এ coordinator workflow ধরে; choreography-তে events chain হয়। Timeout-এ outcome unknown হতে পারে, তাই provider status query/reconciliation লাগবে। Pending, compensated ও needs-review state রাখুন। 2PC concept জানুন; তার blocking ও coordination cost বুঝে ব্যবহার করুন।

Reserve↓Pay↓Ship↓Compensate / reconcile

উদাহরণ

Reserve stock → authorize payment → create shipment। Shipment fail হলে stock release ও authorization void করা যায়। ইতোমধ্যে parcel পাঠানো হলে return process আলাদা।

কখন ব্যবহার করবেন

একাধিক service বা external provider-সহ business workflow।

Trade-off

Coordination ও audit সহজ করতে orchestrator কার্যকর; coordinator reliability ও state management দরকার। Event chain loose coupling দেয় কিন্তু flow বোঝা কঠিন হতে পারে।

সাধারণ ভুল

নিজে করুন

Partial failures, timeout ambiguity ও retry budgets

ফোনে “শুনতে পাচ্ছি না” মানে অন্যজন আপনার কথা শোনেননি—এটি নিশ্চিত নয়।

ধারণা ও কাজের ধাপ

এক অংশ healthy, আরেক অংশ slow/down—distributed system-এ partial failure সাধারণ। Request server-এ complete হয়ে response হারাতে পারে। Timeout outcome unknown জানায়; failure নিশ্চিত করে না। Request deadline পুরো chain-এ propagate করলে user চলে যাওয়ার পরও অযথা work কমে।

Bounded retries, exponential backoff, jitter, retry budget ও idempotency একসঙ্গে ভাবুন। পাঁচ layer প্রত্যেকে তিন attempt করলে worst case fan-out 3^5 হতে পারে। Retry একটি নির্বাচিত layer-এ centralize করা যুক্তিযুক্ত হতে পারে। Load shedding/partial response criticality অনুযায়ী ব্যবহার করুন।

Call + deadline↓Outcome uncertain↓Bounded safe retry↓Query / reconcile

উদাহরণ

Payment provider timeout-এর পরে আবার নতুন transaction না খুলে একই idempotency intent দিয়ে status query বা safe retry করুন। External outcome pending state-এ রেখে reconcile করুন।

কখন ব্যবহার করবেন

যেকোনো remote dependency ও distributed workflow।

Trade-off

Retry recovery সাহায্য করে কিন্তু overload ও duplicate risk বাড়ায়।

সাধারণ ভুল

Timeout হলে নিশ্চিত refund বা নতুন charge করা।

নিজে করুন

এক request commit-এর আগে ও পরে response loss-এর দুটি timeline লিখুন।

মনে রাখুন

Timeout বলে জানি না; idempotency ও reconciliation দিয়ে জানব।

Distributed systems · নতুন পাঠ

Quorum: R + W > N এবং সীমাবদ্ধতা

কয়েকটি copy থেকে পড়া-লেখার সেট overlap করলে latest তথ্য খোঁজার সুযোগ হয়; কিন্তু overlap একাই সব consistency guarantee নয়।

ধারণা ও কাজের ধাপ

N replicas, W required write acknowledgements, R read responses। Fixed replica set-এ R+W>N হলে যেকোনো read/write quorum-এর overlap থাকে। W>N/2 হলে write quorums-ও overlap করে। এই arithmetic network বা concurrent writes নিজে resolve করে না।

Version comparison, concurrent write resolution, membership changes, stale responses, sloppy quorum, repair ও protocol semantics গুরুত্বপূর্ণ। Quorum overlap alone linearizability প্রমাণ নয়। Read repair/anti-entropy convergence সহায়ক হতে পারে; exact guarantee implementation-dependent।

Replica set N↓Write quorum W↓Read quorum R↓Version + conflict rules

উদাহরণ

N=3,W=2,R=2-এ overlap বাধ্যতামূলক। একটি node unreachable হলেও quorum সম্ভব। N=3,W=1,R=1-এ read latest write পাওয়া নিশ্চিত নয়।

কখন ব্যবহার করবেন

Replicated store-এর read/write policy বোঝা।

Trade-off

বড় R/W coordination ও latency বাড়াতে পারে; unreachable replicas-এ availability কমে।

সাধারণ ভুল

R+W>N দেখিয়েই all operations strongly consistent দাবি।

নিজে করুন

ল্যাবে R/W/N বদলান। Read set এবং write set নিজে এঁকে overlap দেখান।

Raft consensus: terms, log replication ও commit

কে leader তা ঠিক করা আর কোন পরিবর্তন সবাই গ্রহণ করল তা ঠিক করা—সম্পর্কিত কিন্তু পৃথক কাজ।

ধারণা ও কাজের ধাপ

Raft nodes follower/candidate/leader role-এ থাকে। Term monotonically বাড়ে; election-এ একই term-এর majority votes লাগে। Leader log entry replicate করে এবং protocol-এর commit rules অনুযায়ী committed entries state machine-এ apply হয়। শুধু leader memory-তে লেখা success-এর যথেষ্ট প্রমাণ নয়।

Log matching ও leader completeness safety rules history consistency বজায় রাখে। Majority available না থাকলে progress থামতে পারে, safety তবুও রক্ষার লক্ষ্য। পাঁচ node quorum cluster সাধারণ non-Byzantine assumptions-এ দুই node unavailable সহ progress করতে পারে, network conditions ও configuration মিলে গেলে। Raft malicious Byzantine behaviour tolerate করার protocol নয়।

Election term↓Majority leader↓Replicate log↓Commit + apply

উদাহরণ

৫ node-এ isolated দুইজন majority পায় না। অন্য তিনজন leader নির্বাচন করে committed log এগোতে পারে। Disconnected পুরোনো leader-কে authoritative নতুন writes accept করতে দেওয়া যাবে না।

কখন ব্যবহার করবেন

Consensus-backed configuration/metadata stores ও coordination systems বোঝা।

Trade-off

Strong agreement coordination latency ও quorum availability চায়।

সাধারণ ভুল

Raft মানে সব read automatically linearizable; read protocol/configuration না দেখা।

নিজে করুন

৫ node-কে 3/2 ভাগ করে কোন পাশে progress সম্ভব ব্যাখ্যা করুন।

মনে রাখুন

Majority + terms + log rules মিলে consensus।

Leader election, split brain ও fencing

দুজন একসঙ্গে নিজেকে manager ভাবলে একই resource-এ conflicting নির্দেশ যেতে পারে।

ধারণা ও কাজের ধাপ

Leader election একটি coordinator নির্বাচন করে। Heartbeat হারালে node dead নাও হতে পারে; network delay/process pause হতে পারে। Randomized election timeout split votes কমাতে পারে, তবু protocol safety আলাদা rules দিয়ে আসে।

Lease নির্দিষ্ট সময় ownership দেয়, clock/delay assumptions থাকতে পারে। পুরোনো leader pause থেকে ফিরে stale action করলে resource-এর fencing token check তা reject করতে পারে। Token নতুন owner-এর সঙ্গে monotonically বাড়ে এবং downstream protected resource-এ enforce করতে হয়; শুধু log-এ token লেখা যথেষ্ট নয়।

Acquire ownership↓New fencing token↓Protected write↓Reject stale owner

উদাহরণ

Scheduler worker A-এর lease expire, B নতুন token8 পায়। A token7 নিয়ে storage update করতে গেলে storage reject করবে। Storage token না দেখলে lease alone stale write আটকায় না।

কখন ব্যবহার করবেন

Schedulers, singleton job, shared resource ownership।

Trade-off

Coordination correctness সাহায্য করে; dependency outage-এ কাজ থামতে পারে।

সাধারণ ভুল

একটি Redis lock মানেই সব process pause/partition-এ exclusive external effect guaranteed।

নিজে করুন

পুরোনো leader pause ও resume-এর timeline-এ fencing কোথায় enforce হবে আঁকুন।

মনে রাখুন

2PC: prepare, commit ও in-doubt state

দুটি খাতায় একসঙ্গে সিদ্ধান্ত নিতে চাইলে সবাই প্রস্তুত কিনা এবং final সিদ্ধান্ত কী—দুটি ধাপ লাগে।

ধারণা ও কাজের ধাপ

Two-phase commit-এ coordinator participants-কে prepare জিজ্ঞেস করে। Participants local resources reserve/log করে yes/no জানায়। সবাই প্রস্তুত হলে coordinator durable decision নিয়ে commit জানায়, নইলে abort। Atomic commitment নির্দিষ্ট participants/protocol assumptions-এর scope-এ।

Prepare-এর পরে decision জানা না গেলে participant in-doubt হয়ে locks/resources ধরে রাখতে পারে। Coordinator recovery, durable logs ও timeout protocol গুরুত্বপূর্ণ। Arbitrary payment/email provider সাধারণত আপনার DB transaction-এর participant নয়। Consensus ও 2PC আলাদা problem; consensus-backed coordinator থাকলেও সব integration transactional হয়ে যায় না।

Prepare request↓Participants vote↓Durable decision↓Commit / abort

উদাহরণ

দুটি transactional DB participant একই transfer-এ prepare হলো। Coordinator হারালে recovery পর্যন্ত অংশগ্রহণকারী অপেক্ষা করতে পারে। এর সঙ্গে external shipment rollback সম্ভব ধরে নেওয়া যাবে না।

কখন ব্যবহার করবেন

Supported distributed transaction environment-এর trade-off বোঝা।

Trade-off

Atomic decision বনাম blocking/latency/coordination cost।

সাধারণ ভুল

2PC ও saga একই; অথবা timeout হলেই participant independently commit করতে পারে ভাবা।

নিজে করুন

Prepare-এর আগে ও পরে coordinator crash হলে participant state লিখুন।

মনে রাখুন

Prepare-এ প্রতিশ্রুতি; decision না জানা পর্যন্ত uncertainty।

Logical clocks, causality ও distributed locks

দুটি ঘড়ি মিললেই ঘটনা কোনটি অন্যটির কারণ তা জানা যায় না।

ধারণা ও কাজের ধাপ

Wall-clock timestamp human time দরকারে উপযোগী কিন্তু skew/rollback থাকে। Lamport clock causal order হলে timestamp order রাখতে পারে; বিপরীত inference সবসময় সত্য নয়। Vector clocks concurrent versions শনাক্তে সাহায্য করতে পারে, metadata cost বাড়ে। Per-entity sequence অনেক practical workflow-তে যথেষ্ট।

Distributed lock ব্যবহারে expiry, renewal, process pause, ownership verification ও downstream fencing ভাবুন। Critical correctness যদি DB constraint/atomic update-এ করা যায়, শুধু lock layer দিয়ে জটিল করবেন না। Lock release-এ ownership token মেলানো জরুরি; অন্যের নতুন lock delete করবেন না।

Concurrent events↓Clock / version metadata↓Ownership lease↓Guard + fencing

উদাহরণ

A lock নিয়ে pause হলো; TTL শেষ, B lock পেল। A ফিরে এসে blind delete করলে B-এর lock মুছতে পারে। Compare-owner-and-delete atomic operation প্রয়োজন।

কখন ব্যবহার করবেন

Cross-node coordination, version conflicts ও sequencing।

Trade-off

More ordering metadata/coordination মানে complexity; প্রয়োজনের চেয়ে global order চাইবেন না।

সাধারণ ভুল

সব distributed race-এর universal solution lock।

নিজে করুন

এক lease expiry race-এ lock ownership, token ও database guard লিখুন।

মনে রাখুন

সময়, causal order ও ownership—আলাদা guarantee।

Authentication, session ও token lifecycle

Authentication জিজ্ঞেস করে “আপনি কে?” Token থাকলেই সেই token-ধারী সব কাজ করতে পারবেন না।

ধারণা ও কাজের ধাপ

Password নিরাপদ password-hashing algorithm দিয়ে রাখুন; plaintext বা দ্রুত সাধারণ hash নয়। Server session-এ opaque ID cookie-তে থাকে, state server-এ। JWT signed claims বহন করে; signature validation, expiry, issuer ও audience যাচাই জরুরি।

OAuth2 delegated authorization framework; OIDC তার ওপর identity layer যোগ করে। Browser cookie-তে Secure, HttpOnly ও উপযুক্ত SameSite policy ব্যবহার করুন। Refresh token rotation, logout, revocation ও stolen token-এর response plan প্রয়োজন।

Credentials / IdP↓Session / token↓Validated request↓Expiry / revoke

উদাহরণ

Employee login করে session পান। পরে employee disabled হলে শুধু browser থেকে token মুছে দিলেই সব device revoke হয় না; server-side revocation/session policy লাগবে।

কখন ব্যবহার করবেন

Web/mobile sign-in ও enterprise identity integration-এ।

Trade-off

Stateless access token request validation সহজ করতে পারে; তাৎক্ষণিক revocation কঠিন হতে পারে। Session central state রাখে কিন্তু lookup ও availability দরকার।

সাধারণ ভুল

JWT payload decode করেই বিশ্বাস করা; token URL/log-এ ফাঁস করা।

নিজে করুন

Login, refresh, logout, disabled user এবং expired token-এর flow আঁকুন। কোথায় secret রাখা হবে লিখুন।

মনে রাখুন

Identity প্রমাণ করুন, token-এর জীবনচক্রও design করুন।

SQL injection, XSS, CSRF ও SSRF

ভিন্ন আক্রমণ ভিন্ন boundary ভাঙে। শুধু একটি “security middleware” দিয়ে সব বন্ধ হয় না।

ধারণা ও কাজের ধাপ

SQL injection-এ untrusted input query structure বদলায়; parameterized queries ব্যবহার করুন। XSS-এ attacker script browser context-এ চলে; output encoding, safe rendering ও CSP defence-in-depth। CSRF browser-এর ambient credentials ব্যবহার করে unwanted action ঘটায়; token/origin checks ও cookie policy প্রয়োজনমতো দিন।

SSRF-এ server-কে attacker-selected destination fetch করানো হয়। Allowlist, resolved destination checks, redirect policy ও network egress control ব্যবহার করুন। Internal/metadata address block করতে DNS resolution ও rebinding risk বিবেচনা করুন।

Encryption at rest, backup encryption ও key management transport TLS-এর থেকে আলাদা। Least privilege, rotation, audit ও compromised-key response লিখুন। Encryption sensitive data read করার অনুমতি নির্ধারণ করে না; authorized service decrypt করতে পারলে তার access policy-ও ঠিক থাকতে হবে।

Untrusted input↓Context boundary↓Validation / encoding↓Restricted execution

উদাহরণ

“Import image from URL” feature দিয়ে internal admin endpoint fetch করা গেলে SSRF হতে পারে। Input URL দেখতে সাধারণ মনে হলেই destination safe নয়।

কখন ব্যবহার করবেন

Forms, rich text, external URL import ও authenticated browser actions-এ।

Trade-off

Input restriction capability কমাতে পারে; rich features রাখলে sanitization ও boundary controls বাড়ে।

সাধারণ ভুল

HTML encode করা SQL injection ঠেকায় ভাবা; CORS-কে authentication মনে করা।

নিজে করুন

নিজের app-এর একটি input কোথায় যায় trace করুন—SQL, HTML, shell, network। প্রতিটি context-এর defence লিখুন।

মনে রাখুন

Input কোন context-এ যাবে, সেই boundary রক্ষা করুন।

সঠিক উত্তর: SSRF

ফাইল বড়, user input অবিশ্বস্ত এবং download link অন্যের হাতে যেতে পারে—তিনটি সমস্যা একসঙ্গে ভাবতে হয়।

ধারণা ও কাজের ধাপ

Presigned upload URL দিয়ে client সরাসরি object storage-এ file পাঠাতে পারে। Server ownership, size policy, expiry ও object key scope ঠিক করবে। Content type শুধু extension দেখে বিশ্বাস করবেন না; প্রয়োজনমতো inspect, scan ও quarantine করুন।

Private object-এর download permission server যাচাই করে short-lived signed link দিতে পারে। Link মেয়াদ পর্যন্ত bearer access হতে পারে, তাই log/referrer leakage বিবেচনা করুন। Credentials source control-এ নয়; managed secret store/configuration, least privilege ও rotation ব্যবহার করুন।

Retention lifecycle tiering, file checksum/integrity verification ও restore test যোগ করুন। Client-provided filename/object key trusted নয়; server-generated scoped key ব্যবহার করুন। Download URL-এর expiry access revoke-এর exact behaviour backend/CDN policy দিয়ে যাচাই করতে হবে।

Authorize↓Direct upload↓Validate / scan↓Private download

উদাহরণ

User upload complete বললেই document ready নয়। Worker scan/parse করে status ready করবে। Tenant-scoped metadata object ownership ধরে রাখবে।

কখন ব্যবহার করবেন

Profile image, PDF, report export ও AI document ingestion।

Trade-off

Direct upload API bandwidth কমায়, কিন্তু completion validation, orphan cleanup ও async status দরকার।

সাধারণ ভুল

Object key অনুমান করা কঠিন হলেই private ভাবা; permanent public URL-এ sensitive report রাখা।

নিজে করুন

Upload request → signed URL → upload → verify → scan → ready → authorized download flow আঁকুন।

মনে রাখুন

Upload শেষ ≠ ফাইল নিরাপদ ≠ সবাই দেখতে পারবে।

SLI, SLO, SLA ও error budget

“Server up” থাকলেও booking fail হলে user-এর কাছে service ভালো নয়। Reliability user journey দিয়ে মাপুন।

SLI measurement: valid booking requests-এর কত শতাংশ সফল হলো। SLO সেই indicator-এর target ও time window। SLA contractual commitment হতে পারে, violation-এর consequence থাকে। Availability SLI-তে eligible requests ও excluded errors পরিষ্কার সংজ্ঞা দিন।

Error budget হলো অনুমোদিত unreliability। ৩০ দিনে time-based 99.9% target হলে unavailable time budget ৪৩.২ মিনিট। Request-based SLO-তে request সংখ্যা ব্যবহার হবে; দুটো মিশিয়ে ফেলবেন না। Burn-rate alert budget অস্বাভাবিক দ্রুত খরচ হলে সতর্ক করতে পারে।

User journey↓SLI measurement↓SLO + budget↓Alert / prioritize

Recovery, RPO/RTO ও incident response

Backup file আছে—এটি recovery হওয়ার প্রমাণ নয়। নতুন environment-এ restore করে ব্যবহারযোগ্য data পেলে প্রমাণ পাওয়া শুরু হয়।

ধারণা ও কাজের ধাপ

RPO সর্বোচ্চ গ্রহণযোগ্য data loss-এর সময়সীমা; RTO service restore-এর target duration। Backup schedule, retention, encryption, access এবং restore test সেই প্রয়োজন থেকে design করুন। Replica accidental deletion-ও copy করতে পারে, তাই independent backup দরকার।

Incident-এ প্রথমে impact ও scope যাচাই, mitigation, communication, recovery, পরে root cause ও follow-up। Circuit breaker unhealthy dependency-তে repeated call সীমিত করে; bulkhead resource pool আলাদা রেখে failure ছড়ানো কমায়। Half-open recovery probe সীমিত রাখুন।

Disaster recovery-তে cold standby কম চলতি খরচ কিন্তু restore ধীর; warm standby কিছু infrastructure প্রস্তুত রাখে; hot/active setup দ্রুত recovery দিতে পারে কিন্তু replication/coordination খরচ বেশি। Multi-region active-active-এ conflicting writes, traffic cutover, identity ও shared dependencies পরীক্ষা ছাড়া availability দাবি করবেন না। RPO/RTO business journey অনুযায়ী নির্ধারণ করুন।

Detect impact↓Mitigate / isolate↓Restore + verify↓Postmortem / actions

উদাহরণ

প্রতি ২৪ ঘণ্টায় backup হলে recovery-এর ঠিক আগে প্রায় এক দিনের data হারাতে পারেন, অতিরিক্ত log recovery না থাকলে। RPO ৫ মিনিট হলে অন্য ব্যবস্থা দরকার।

কখন ব্যবহার করবেন

Production ownership, critical data ও external dependency failure-এ।

Trade-off

সাধারণ ভুল

Incident-এর সময় প্রমাণ ছাড়া data delete/restart করে investigation কঠিন করা; restore কখনো test না করা।

নতুন DB-তে backup restore, app start ও ৫টি data check করুন। সময় মেপে target-এর সঙ্গে তুলনা করুন।

মনে রাখুন

Service discovery ও dynamic endpoints

ধারণা ও কাজের ধাপ

Service instances ephemeral হতে পারে। Registry বা DNS/service abstraction logical name থেকে healthy endpoints দেয়। Client-side discovery client list থেকে target নেয়; server-side discovery proxy/load balancer সেই দায়িত্ব নেয়। Registration, heartbeat, deregistration ও stale cache behaviour লিখুন।

Discovery-এর সঙ্গে health/connection lifecycle এক করুন। DNS cache পুরোনো endpoint ধরে রাখতে পারে; existing connections drain করতে হয়। Discovery store unavailable হলেও cached endpoints কিছু সময় চলতে পারে, কিন্তু safety/freshness policy স্পষ্ট দরকার।

Logical service name↓Discovery / registry↓Healthy endpoints↓Client / proxy selection

উদাহরণ

Report worker নতুন instance যোগ হলো। API hard-coded IP না ধরে reports.service logical address ব্যবহার করে। Deployment-এর পরে old IP cached থাকলে কিছু request fail করতে পারে।

Autoscaling, orchestration ও multi-service environments।

Trade-off

নিজে করুন

ধারণা ও কাজের ধাপ

Circuit closed-এ calls যায় ও failures count হয়। Threshold পেরোলে open-এ fail-fast/fallback। Cooldown শেষে half-open-এ সীমিত probe; success হলে closed, failure হলে আবার open। Sliding window, minimum sample ও slow-call policy configuration অনুযায়ী।

Bulkhead আলাদা thread/connection/concurrency pool রাখে, যাতে noncritical report সব resources খেয়ে payment বন্ধ না করে। Timeout অপেক্ষা bound করে, retry transient failure সামলায়, circuit repeated pressure কমায়—এগুলো পরস্পরের বিকল্প নয়। Fallback stale/partial হতে পারে; মিথ্যা business success নয়।

Closed: calls↓Failure threshold↓Open: reject↓Half-open probe

উদাহরণ

Recommendation provider down। Circuit open হলে homepage recommendation ছাড়া চলতে পারে। Payment provider down হলে “paid” fake fallback নয়; pending/unavailable status দেখান।

কখন ব্যবহার করবেন

Remote dependency failures ও cascading outage prevention।

Trade-off

সাধারণ ভুল

নিজে করুন

Cost estimation, TCO ও unit economics

Server bill-ই পুরো খরচ নয়। Storage, traffic, licenses, operations ও মানুষজনের সময়ও লাগে।

ধারণা ও কাজের ধাপ

Total cost-এ compute hours, DB/storage/backup, network egress, managed service requests, logs, licenses ও operational labour আলাদা ধরুন। Cost model-এর unit, region, currency ও assumption স্পষ্ট লিখুন। এখানে example rates কাল্পনিক; live provider price নয়।

Unit economics: total relevant monthly cost / successful tasks। Idle baseline ও variable cost আলাদা রাখুন। Peak capacity, growth, retention ও disaster recovery যোগ করুন। Managed service-এর বেশি bill engineering effort কমাতে পারে; self-hosting-এর কম bill human operations cost বাদ দিলে misleading।

Workload assumptions↓Fixed + variable costs↓Operational TCO↓Cost per successful task

উদাহরণ

কাল্পনিক: compute200 + DB100 + storage30 + egress70 + monitoring50 = 450 units/month। 90,000 successful job হলে infra cost/job0.005 units; support/labour বাদ থাকলে তা স্পষ্ট বলুন।

Architecture comparison, budget এবং AI inference pricing।

Trade-off

Cost কমাতে caching/batching quality, latency ও freshness বদলাতে পারে।

Case study: URL shortener

Long URL থেকে short code, redirect ও analytics—ছোট product-এ অনেক design decision দেখা যায়।

ধারণা ও কাজের ধাপ

প্রথমে scope: create URL, redirect, optional expiry/custom alias। Estimate read/write ratio। POST /urls create, GET /:code redirect। Data: code unique, target, owner, created_at, expires_at, status। Generated ID Base62 encode করলে ছোট representation পাওয়া যায়; random code-এ collision retry/constraint দরকার।

Redirect path cache-aside হতে পারে। Expiry/disabled state enforce করুন। 301 স্থায়ী caching-এর প্রভাব বিবেচনা করুন, mutable links-এ 302/appropriate cache policy। Click analytics queue-তে পাঠালে redirect latency কম থাকতে পারে; analytics loss tolerance লিখুন।

Create / redirect API↓Code + policy↓Cache → mapping DB↓Async click analytics

উদাহরণ

Client → CDN/proxy → redirect service → Redis → DB। Create path-এ validation, abuse controls, rate limit। Analytics consumer aggregates তৈরি করে; redirect-এর correctness analytics-এর ওপর আটকে থাকবে না।

ML system: data থেকে serving

Model training শেষ মানেই usable ML product শেষ নয়। Input, evaluation, deployment ও monitoring বাকি থাকে।

ধারণা ও কাজের ধাপ

Data source → validation → labels/features → train/validation/test split → training → evaluation → model registry → serving। Split-এর আগে duplicate/user/time leakage পরীক্ষা করুন। Temporal problem-এ future data training-এ মেশাবেন না। Experiment-এ dataset version, config, code ও model artifact রাখুন।

Batch inference নির্ধারিত সময়ে অনেক prediction করে; online request latency-sensitive। Training-serving skew হলে offline metrics ভালো হলেও live quality খারাপ হতে পারে। Drift signal মানেই automatic retraining নয়; labels ও performance evidence দরকার।

Versioned data↓Train / evaluate↓Registry↓Serve / monitor

উদাহরণ

Support ticket classifier-এ একই ticket-এর duplicate train ও test-এ গেলে score misleading হবে। Baseline rules/classical model-এর সঙ্গে comparison করুন।

কখন ব্যবহার করবেন

Classification, fraud scoring, recommendation ও model-backed API।

Trade-off

More complex model quality বাড়াতে পারে, কিন্তু latency, cost ও maintenance বাড়ে। Business metric ও safety constraints একসঙ্গে দেখুন।

সাধারণ ভুল

Accuracy একমাত্র metric; imbalanced dataset-এ rare critical class উপেক্ষা।

নিজে করুন

Ticket classifier-এর split policy, precision/recall, artifact version, rollback ও monitoring লিখুন।

মনে রাখুন

Data quality → honest evaluation → reliable serving।

RAG: retrieval, permissions ও evaluation

Model-এর মুখস্থ জ্ঞান বদলানোর বদলে প্রশ্নের জন্য প্রাসঙ্গিক document খুঁজে context দেওয়া হয়।

ধারণা ও কাজের ধাপ

Ingestion-এ parse, chunk, metadata, embeddings ও index। Query-তে authenticated scope দিয়ে retrieve; keyword/vector hybrid ও reranking প্রয়োজনমতো। Model retrieved evidence থেকে answer ও citation দেয়; প্রমাণ না থাকলে abstain করতে শেখান।

Document-কে untrusted input ধরুন। “Ignore previous instruction” লেখা document authorization দিতে পারে না। Retrieval-এর আগে/সময় tenant ও document permission enforce করুন। Deleted document-এর index cleanup ও reindex versioning দরকার। Retrieval recall এবং answer correctness আলাদাভাবে evaluate করুন।

Question + identity↓Permission-aware retrieval↓Ranked evidence↓Answer + citations

উদাহরণ

HR policy assistant salary policy থেকে উত্তর দিতে পারে, কিন্তু employee-এর অনুমতি ছাড়া private payroll document context-এ আনতে পারবে না। ভালো answer-ও unauthorized source leak করলে failure।

কখন ব্যবহার করবেন

Changing/private knowledge থেকে grounded answer দিতে।

Trade-off

বড় chunk context দেয় কিন্তু irrelevant text বাড়ায়। ছোট chunk precise হতে পারে কিন্তু context হারায়। Top-k বাড়ালে cost ও noise বাড়ে।

সাধারণ ভুল

Vector similarity-কে truth বা permission ভাবা; শুধু কয়েকটি সুন্দর demo answer দিয়ে quality বিচার।

নিজে করুন

RAG lab-এ tenant ও permission filter বদলান। এরপর ২০টি question-এ retrieval hit, answer quality ও unauthorized exposure আলাদা score করুন।

Fine-tuning: baseline থেকে measurable improvement

কোন task ভালো করতে চান তা না জানলে fine-tuning-এর success মাপা যাবে না।

ধারণা ও কাজের ধাপ

প্রথমে prompt/rules/base model baseline। Task-specific clean examples, consistent labels/output format এবং train/validation/test split তৈরি করুন। LoRA কমসংখ্যক adapter parameters train করে; QLoRA quantized base-এর ওপর adapter training-এর পদ্ধতি। Full training-এর তুলনায় resource requirements কমতে পারে, কিন্তু dataset ও evaluation এখনও জরুরি।

Learning rate, effective batch size, sequence length, checkpoint ও seed record করুন। Train loss কমলেও validation খারাপ হলে overfitting হতে পারে। Quality, per-class errors, latency ও cost দিয়ে baseline compare করুন। Model/data license এবং sensitive training data-র অনুমতি যাচাই করুন।

Baseline↓Clean split↓Train adapter↓Held-out comparison

উদাহরণ

Invoice field extraction-এ valid JSON মানেই সঠিক amount নয়। Exact field metrics ও missing/incorrect value দেখুন। নতুন knowledge প্রতিদিন বদলালে RAG প্রয়োজন হতে পারে; fine-tuning সব ক্ষেত্রে বিকল্প নয়।

কখন ব্যবহার করবেন

Stable task behaviour, formatting বা domain task-এ baseline যথেষ্ট না হলে।

Trade-off

Better task fit পাওয়া যেতে পারে; training cost, regressions ও version management যোগ হয়।

সাধারণ ভুল

Test leakage, inconsistent annotation, train loss দিয়ে একা improvement দাবি।

নিজে করুন

একটি ছোট classifier/extractor-এর baseline ও adapter model একই held-out set-এ compare করে failure report লিখুন।

মনে রাখুন

আগে baseline, পরে training, শেষে সৎ comparison।

Inference: batching, GPU memory ও overload

GPU-তে model বসেছে মানেই unlimited request serve করা যাবে না। Context ও concurrent generation-ও memory খায়।

ধারণা ও কাজের ধাপ

Weights ছাড়াও KV cache, activations ও runtime overhead memory নেয়। Quantization weights কমাতে পারে কিন্তু quality ও hardware support পরীক্ষা করতে হয়। Batch throughput বাড়াতে পারে, তবে অপেক্ষা/latency trade-off থাকে।

TTFT প্রথম token-এর সময়, inter-token latency পরের tokens-এর গতি, throughput মোট কাজের হার। Admission control, max context/output, cancellation, bounded queue ও timeout দিন। Model warmup, cold start, version rollout ও fallback policy লিখুন। GPU lab সরল memory model; বাস্তব engine profiling প্রয়োজন।

Request budget↓Bounded queue↓GPU engine↓Stream / cancel / monitor

উদাহরণ

একটি long prompt-এর user memory দখল করলে অন্য user-এর latency বাড়তে পারে। Tenant quota ও token budget request count-এর চেয়ে ভালো resource proxy হতে পারে, workload অনুযায়ী।

কখন ব্যবহার করবেন

Self-hosted LLM, online ML service ও expensive AI workflows।

Trade-off

আরও concurrency utilization বাড়াতে পারে; memory pressure ও latency-ও বাড়ে। Cheaper fallback-এর quality আলাদা হবে।

সাধারণ ভুল

শুধু model weights-এর size দেখে GPU নির্বাচন; unlimited queue বা output tokens।

নিজে করুন

Inference lab-এ GPU memory, weights ও per-request budget বদলান। বাস্তব test-এ TTFT, tokens/s, p95, errors এবং quality একসঙ্গে লিখুন।

Interactive lab খুলুন →

মনে রাখুন

Quality + latency + memory + cost—চারটিই serving design।

Guided mock ২: webhook delivery platform

Customer endpoint slow বা offline হলেও accepted event হারাবে না—এই প্রতিশ্রুতির design করুন।

ধারণা ও কাজের ধাপ

Prompt: producers event submit করবে; subscribers-এর HTTPS endpoint-এ delivery। Clarify ordering, retry window, payload retention, signatures, quotas ও delivery guarantees। Reference: authenticated ingestion→durable event/subscription record→queues→bounded workers→attempt log→DLQ/replay।

Signed webhook, endpoint ownership, SSRF/egress controls, retries/backoff+jitter, per-subscriber isolation ও idempotency ID দিন। Delivery at-least-once হলে receiver contract-এ duplicate handling লিখুন। Rubric: contract2, durability2, security2, overload2, recovery2।

Durable ingestion↓Tenant-aware scheduling↓Signed bounded delivery↓Attempt audit + replay

উদাহরণ

এক subscriber ৩০ সেকেন্ড অপেক্ষা করায় সব worker আটকে যাচ্ছে। Per-subscriber concurrency/timeouts ও bulkhead দিলে অন্য customers-এর delivery চলতে পারে।

কখন ব্যবহার করবেন

Async delivery, external integration ও FDE-type problem solving।

Trade-off

Long retry window recovery বাড়ায়; storage, delays ও user support load বাড়ে।

সাধারণ ভুল

Customer URL blindly fetch করে internal network access দেওয়া।

নিজে করুন

আপনার design-এ ৫টি crash/timeout বসান; event state ও retry policy লিখুন।

মনে রাখুন

Accept durable, deliver bounded, retry visible।

Quiz: এক slow subscriber-এর প্রভাব কীভাবে সীমিত করবেন?
